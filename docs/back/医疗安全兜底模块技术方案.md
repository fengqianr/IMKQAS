# 医疗安全兜底模块技术方案

> **版本**：2.0 | **更新日期**：2026-07-13 | **状态**：已实现

## 一、背景与必要性

RAG 系统在医疗场景下的核心风险：当检索不到可靠信息时，LLM 可能基于不相关或错误上下文生成看似合理但实际危险的回答。此外，用户可能询问急症症状，系统若按常规流程回答会延误救治。

本模块实现**四层安全防护**：
1. **急症关键词预检**（检索前）——零延迟阻断高危查询
2. **置信度门控**（检索后、LLM前）——基于检索质量决定是否调用LLM
3. **回答安全校验**（LLM后）——净化危险内容、添加免责声明
4. **禁忌检测兜底**（响应构建时）——药物-人群禁忌规则表的兜底安全提示

配套建设了**离线评估体系**和**在线指标采集**系统，用于持续监控安全兜底的有效性和误判率。

**必要性（应对面试追问）：**

- *问：医疗 RAG 为什么需要专门的兜底模块？* 答：通用 RAG 的置信度计算通常在 LLM 生成之后，但医疗场景需要在 LLM 生成**之前**就阻断低质量检索——因为一旦 LLM 开始生成，即使答案质量差，用户也可能采信。同时，急症检测必须在检索之前完成，零延迟响应。
- *问：阈值为什么设成 0.35/0.6？* 答：Cross-encoder 重排序分数在 [0,1] 区间，< 0.3 通常表示语义不相关，0.3-0.6 为弱相关，> 0.6 为可靠相关。医疗场景取保守值 0.35 作为硬阻断线（留 0.05 缓冲），0.6 作为免责提示线。这些值应在上线后通过 A/B 测试调优。
- *问：会不会误判？* 答：会，任何基于关键词/阈值的系统都有误判可能。设计上做了四层缓冲：(1) 急症检测仅阻断明确的高危关键词，不阻断模糊描述；(2) 低置信度阻断仅在 top-1 分数 < 0.35 时生效，保留 LLM 在弱相关时生成带免责提示的回答的权利；(3) 所有阻断返回友好就医建议而非报错；(4) 通过在线指标采集和离线评估持续监控误判率并调优阈值。

### 2.2 安全兜底在 QaServiceImpl 中的插入位置

| 插入点 | 步骤编号 | 方法调用 | 作用 | 可用数据 |
|--------|---------|---------|------|----------|
| A | [3] | `safetyGuardService.checkEmergency(query)` | 急症关键词检测 | 仅 query 字符串 |
| B | [9] | `safetyGuardService.assessConfidence(rerankedResults)` | 检索质量门控 | rerankedResults (score/vectorScore/keywordScore) |
| C | [12] | `safetyGuardService.sanitizeAnswer(answer, confidence)` | 回答安全校验 | answer 字符串 + confidence |
| D | 兜底 | `contraindicationDetectionService.buildSafetyNote(query)` | 禁忌规则兜底 | query 字符串 |

**说明**：`answerWithSources()` 方法中安全兜底的集成位置与 `answer()` 完全一致，同时在管线追踪中记录更详细的中间状态数据。

| 文件 | 说明 |
|------|------|
| `src/main/java/com/student/config/SafetyConfig.java` | 配置类，绑定 `imkqas.rag.safety` 前缀，含 `EmergencyConfig` / `ConfidenceConfig` / `AnswerSafetyConfig` 三个内部类 |
| `src/main/java/com/student/service/rag/SafetyGuardService.java` | 核心服务，实现 `checkEmergency()` / `assessConfidence()` / `sanitizeAnswer()` 三层安全防护 |
| `src/main/java/com/student/service/rag/SafetyDecision.java` | 急症预检值对象：`blocked` / `reasonCode` / `adviceMessage` / `severityLevel` |
| `src/main/java/com/student/service/rag/ConfidenceDecision.java` | 置信度门控值对象：`blocked` / `warning` / `maxScore` / `message` |

**关键设计决策**：
- `assessConfidence` 使用 `List<?>` 而非具体类型——编译期解耦，运行时 `instanceof` 检查
- 正则模式通过 `ConcurrentHashMap` 缓存编译结果，避免重复编译
- 统计计数器（`AtomicInteger`）为 `OnlineMetricsCollector` 提供数据源
- 免责声明通过 `endsWith` 检查防止重复拼接

## 五、与现有 RAG 链路的集成

### 5.1 集成架构

安全兜底模块深度嵌入 `QaServiceImpl` 的两个核心方法：
- `answer()` —— 基础问答接口
- `answerWithSources()` —— 带来源引用的问答接口

两个方法采用**相同的安全兜底插入位置**，区别在于 `answerWithSources()` 在管线追踪中记录更详细的中间状态数据（含步骤耗时、输入输出计数、中间数据 Map）。

### 5.2 answer() 方法中的安全兜底流程

```
answer(query, userId, conversationId)
  │
  ├─ [1] IntentRouter.classify()          → DATA_COLLECTION时直接返回，不走RAG
  ├─ [2] QueryRewriteService.rewrite()     → 查询预处理
  │
  ├─ [3] safetyGuardService.checkEmergency(processedQuery)   ← 插入点A
  │     └─ blocked → buildEmergencyResponse() → 直接返回
  │
  ├─ [4][5] retrieveDocuments()           → 双路召回+RRF融合
  ├─ [6] qualityFilterService.filter()    → 质量过滤
  ├─ [7] qualityFilterService.detectContradictions()  → 矛盾检测（权威分级裁决，不阻断管线）
  ├─ [8] rerankDocuments()               → 多因子重排序
  │
  ├─ [9] safetyGuardService.assessConfidence(rerankedResults)  ← 插入点B
  │     └─ blocked → buildLowConfidenceResponse() → 直接返回
  │
  ├─ [10] semanticCacheService.get()      → 语义缓存检查
  │       ├─ 命中 → safetyGuardService.sanitizeAnswer(cachedAnswer, 0.8)
  │       └─ 未命中 → 获取重建锁
  │           ├─ 获锁 → LLM生成 → sanitizeAnswer(answer, confidence)  ← 插入点C
  │           └─ 未获锁 → 等待200ms → 重试缓存 → 仍未命中则LLM生成
  │
  ├─ MIXED意图 → 附加问卷推荐
  ├─ contraindicationDetectionService.buildSafetyNote(query)  ← 插入点D
  │
  └─ 返回 QaResponse
```

### 5.3 四种阻断/降级响应

| 响应类型 | 触发条件 | 构建方法 | modelUsed | confidence |
|---------|---------|---------|-----------|------------|
| 急症阻断 | 关键词命中 CRITICAL/HIGH/MEDIUM | `buildEmergencyResponse()` | `"safety-guard"` | 0.0 |
| 低置信度阻断 | maxScore < 0.35 | `buildLowConfidenceResponse()` | `"safety-guard"` | maxScore |
| 矛盾检测 | 药物-人群矛盾检测命中 | LLM正常生成 + `buildContradictionNote()` 附加安全提示 | 正常 modelUsed | 正常 confidence |
| 异常降级 | 管线抛出异常 | `getFallbackResponse()` | `"fallback"` | 0.1 |

### 5.4 语义缓存中的安全处理

缓存命中时不跳过安全校验——即使是已缓存的回答，也需要经过 `sanitizeAnswer()` 净化（使用固定置信度 0.8 触发免责声明检查），避免缓存内容因安全规则更新后不再合规。

### 5.5 管线追踪集成

安全兜底的三个步骤在 `PipelineTraceContext` 中以独立步骤记录：

```java
// 步骤命名规范
PipelineTraceContext.recordStep("安全兜底①-急症预检", 3, durationMs);
PipelineTraceContext.recordStep("安全兜底②-置信度门控", 9, durationMs);
PipelineTraceContext.recordStep("安全兜底③-答案净化", 12, durationMs);

// answerWithSources 中还记录详细中间数据
PipelineTraceContext.recordStep("安全兜底①-急症预检", 3, durationMs,
    1, 1, Map.of("结果", emergencyDecision.isBlocked() ? "触发阻断" : "通过"));
PipelineTraceContext.recordStep("安全兜底②-置信度门控", 9, durationMs,
    1, 1, Map.of("结果", confidenceDecision.isBlocked() ? "低于阈值，已阻断" : "通过",
           "最高置信度", String.format("%.2f", confidenceDecision.getMaxScore())));
PipelineTraceContext.recordStep("安全兜底③-答案净化", 12, durationMs,
    1, 1, Map.of("结果", wasSanitized ? "已净化（移除风险内容）" : "无需净化",
           "置信度", String.format("%.2f", confidence)));
```

这些跟踪数据被 `OnlineMetricsCollector` 定时消费，聚合为在线指标快照。同时在离线评估中，完整管线的每一步耗时和状态都被持久化到 `eval_pipeline_snapshot` 表。

## 六、三级安全防护全链路

安全兜底不是单点防御，而是贯穿 RAG 管线全生命周期的**三级安全漏斗**——从文档入库到最终回答，每一级都在减少前一级遗漏的风险。

```
文档预处理阶段          检索+重排序阶段           LLM生成+输出阶段
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│ 第一级        │  →   │ 第二级        │  →   │ 第三级        │
│ 来源可信度分级 │      │ 药物-人群冲突  │      │ 置信度门控    │
│ (证据金字塔)   │      │ 检测          │      │ + 回答安全校验 │
│              │      │              │      │ + 免责声明     │
│ AuthorityLevel│      │ Contra-      │      │ SafetyGuard   │
│ 8级金字塔     │      │ indication   │      │ Service       │
│ 0.1 ~ 1.0    │      │ Detection    │      │ 0.35/0.6/0.8  │
└──────────────┘      └──────────────┘      └──────────────┘
    入库时标注             检索后过滤              LLM 后净化
```

### 6.1 第一级：来源可信度分级（证据金字塔）

**文件**：`src/main/java/com/student/service/rag/MultiFactorRerankService.java`（AuthorityLevel 枚举）

在文档预处理阶段，系统根据来源类型为每个文档分片标注权威性分数，写入 chunk 元数据。检索时高权威分片在多因子重排序中获得加权，冲突时高权威覆盖低权威。

#### 8 级证据金字塔

| 等级 | 枚举值 | 权威分数 | 来源类型 |
|------|--------|---------|---------|
| L1 | `SYSTEMATIC_REVIEW` | 1.0 | 系统评价/Meta分析/临床指南（NCCN、中华医学会、NICE、WHO） |
| L2 | `DRUG_LABEL` | 0.95 | 药品说明书（FDA/NMPA） |
| L3 | `RCT` | 0.9 | 随机对照试验 |
| L4 | `COHORT_STUDY` | 0.7 | 队列研究/病例对照研究 |
| L5 | `HOSPITAL_SCIENCE` | 0.6 | 医院官方科普/医学百科（MSD手册、Mayo Clinic） |
| L6 | `EXPERT_OPINION` | 0.5 | 专家意见/病例报告 |
| L7 | `GENERAL_WEBSITE` | 0.3 | 普通网站/自媒体 |
| L8 | `FORUM_QA` | 0.1 | 论坛/问答（百度知道、知乎等） |

#### 权威分数的三种获取方式（优先级从高到低）

1. **元数据直读**：chunk 的 metadata 中 `authority` 字段已有数值 → 直接使用
2. **来源类型映射**：metadata 中 `source_type` 字段 → `AuthorityLevel.fromSourceType()` 映射到对应分数（switch 匹配 `systematic_review` / `drug_label` / `rct` / `cohort_study` / `hospital_science` / `expert_opinion` / `general_website` / `forum`）
3. **内容启发式推断**：以上两者均无时，通过关键词匹配推断：
   - 命中"指南"/"Cochrane"/"NICE"/"WHO"/"FDA"/"NMPA" → 1.0
   - 命中"RCT"/"随机对照" → 0.9
   - 命中"说明书"/"适应证"/"禁忌" → 0.95
   - 命中"研究"/"试验" → 0.7
   - 命中"科普"/"百科" → 0.6
   - 兜底 → 0.3

#### 多因子重排序中的权重

**文件**：`src/main/java/com/student/service/rag/impl/MultiFactorRerankServiceImpl.java`

```java
// calculateFinalScore() 公式
finalScore = 0.3 × authority + 0.15 × timeliness + 0.35 × semantic + 0.2 × intent
```

配置中可调整为 `authority=0.4, timeliness=0.2, semantic=0.4`（见 `RagConfig.MultiFactorRerankConfig`）。权威性权重在四因子中排第二（仅次于语义相似度），确保高权威来源在同等语义相关度下优先展示。

#### 未知来源处理

对于无法判断权威性的来源（metadata 中无 `authority` 也无 `source_type`，内容启发式也未命中）：
- 默认权威分数为 **0.3**（GENERAL_WEBSITE 等级），保守处理
- 不触发审核标记（当前版本未实现后台运营看板，该功能在规划中）

### 6.2 第二级：药物-人群冲突检测

第二级在检索阶段执行，分为**禁忌过滤**和**矛盾检测**两个子环节，均由 `QualityFilterServiceImpl` 实现。

**文件**：
- `src/main/java/com/student/service/rag/impl/QualityFilterServiceImpl.java`（质量过滤 + 矛盾检测）
- `src/main/java/com/student/service/rag/impl/ContraindicationDetectionServiceImpl.java`（禁忌离线标注 + 在线检测）
- `src/main/java/com/student/service/rag/impl/SynonymExpansionServiceImpl.java`（药物/人群术语标准化：LOCAL → SNOMED CT → LLM）
- `src/main/java/com/student/entity/contraindication/DrugPopulationContraindication.java`（禁忌规则实体）
- `src/main/resources/db/migration/V8__Contraindication_rules.sql`（禁忌规则表 + 30+条种子数据）

#### 6.2.1 药物-人群禁忌过滤

**离线阶段**（文档入库时，`DocumentProcessorServiceImpl` 第 111-116 行）：
1. 对每个 chunk 调用 `ContraindicationDetectionService.annotateChunks()`
2. 使用 `MedicalEntityRecognitionService` 抽取 DRUG 和 POPULATION 实体
3. 调用 `SynonymExpansionService.expand()` 统一标准化（LOCAL → SNOMED CT → LLM 三级）
   - 药物和人群标准化均只使用 `medical_synonym_mapping` 表，不再单独查 Drug/DrugAlias 表
   - `expand()` 内部自动将未映射词条写入 `UnmappedTermRecord` 审核队列，供管理员后续标准化
4. 标准化后的名称查规则缓存，标准化失败则用原始文本兜底（不阻断流程）
5. 命中规则的 chunk 标记 `hasContraindication=1`，将匹配详情写入 `contraindicationInfo` JSON 字段

**在线阶段**（检索后，`QualityFilterServiceImpl.applyContraindicationFilter()`）：

```
遍历检索结果：
    │
    ├── hasContraindication == 1
    │   └── 读预标注 JSON → 分级降权/过滤 ✅（快速路径）
    │
    └── hasContraindication == 0 或 null （未标注/标注失败）
        │
        └── 在线实时补偿（realtimeContraindicationEnabled=true 时）：
            1. MedicalEntityRecognitionService.recognize(chunkText) 抽取实体
            2. SynonymExpansionService.expand() 标准化
            3. 标准化后的（药物, 人群）查规则缓存
            4. 命中 → 分级降权/过滤
            5. 未命中 → 放过
```

**补偿路径与预标注使用同一套底层能力**（实体抽取 + 标准化 + 规则匹配），离线能识别的禁忌在线也能识别，安全能力不打折。仅执行时机从"入库时"变为"查询时"。

- 按禁忌类型分级处理：

| 禁忌类型 | 枚举值 | 降权因子 | 处理策略 |
|---------|--------|---------|---------|
| 绝对禁用 | `ABSOLUTE` | 0.0 | **直接丢弃**，不进入 LLM 上下文 |
| 相对禁忌 | `RELATIVE` | 0.3 | 强降权，分数乘以 0.3 |
| 慎用 | `CAUTION` | 0.5 | 弱降权，分数乘以 0.5 |
| 尚不明确 | `UNCLEAR` | 0.7 | 轻微降权，分数乘以 0.7 |

多个匹配取最严重的一个（`getWorstMatch()` 取最小 factor）。

**禁忌规则数据库**（`drug_population_contraindication` 表）：
- 字段：`drug_name`、`population_name`、`contraindication_type`、`evidence_level`、`description`、`source`
- 证据等级：GUIDELINE / DRUG_LABEL / RCT / META_ANALYSIS / EXPERT_CONSENSUS / CASE_REPORT
- 预置 30+ 条种子数据：孕妇禁用利巴韦林/异维A酸/沙利度胺/ACEI/ARB 类、儿童禁用四环素类/喹诺酮类、老人慎用阿司匹林等

#### 6.2.2 断言冲突检测（权威分级裁决）

**文件**：`QualityFilterServiceImpl.detectContradictions()` / `checkDrugPopulationPair()`

同一药物-人群对下，A 文档说"可用"，B 文档说"禁用"时，采用**权威分级裁决**策略：

**检测流程**：
1. 从查询中提取药物实体和人群实体
2. 对每个药物-人群对，在检索结果中分别扫描：
   - 正向断言关键词：可用、安全、适用、推荐、首选、有效、一线
   - 负向断言关键词：禁用、禁忌、不宜、慎用、避免、忌用、不可
3. 确认断言上下文确实包含药物或人群关键词（避免误匹配）
4. 计算正负双方的权威性分数（从 metadata 的 `authority` 字段或 `source_type` 映射获取）
5. **当正负双方权威性均 > 0.7 时**，按权威差距分级处理：

**分级裁决策略**：

| 条件 | 裁决类型 | 处理方式 |
|------|---------|---------|
| `|posAuth - negAuth| ≥ 0.15` | **RESOLVED（已裁决）** | 采纳高权威方表述，管线正常继续，LLM 生成后附加裁决说明 |
| `|posAuth - negAuth| < 0.15` | **UNRESOLVED（未裁决）** | 管线正常继续，LLM 综合判断，回答末尾附加冲突说明 |

**RESOLVED 时的安全提示**（`buildContradictionNote()`）：
> 关于 {药物-人群对}，不同来源存在不同说法。经评估，权威性较高的来源（权威分数 {winnerAuth}）倾向于认为{可用/不宜使用}，以下回答以此为准。

**UNRESOLVED 时的安全提示**（`buildContradictionNote()`）：
> 关于 {药物-人群对}，不同权威来源存在不同说法（权威性相当），以下回答综合了多来源信息。建议您咨询专业医生，结合具体病情做出判断。

**关键设计决策**：
- 权威差距阈值 `AUTHORITY_GAP_THRESHOLD = 0.15`：对应证据金字塔中约一级的差距（L1=1.0 vs L3=0.9，差距 0.1；L3=0.9 vs L4=0.7，差距 0.2）
- 矛盾检测**不再阻断管线**——即使检测到矛盾，也交由 LLM 生成回答，但附加强提示
- `ContradictionResult.ResolutionType` 枚举：`NONE` / `RESOLVED` / `UNRESOLVED`

#### 6.2.3 候选集为空的兜底

当质量过滤后所有候选文档被丢弃（包括因 ABSOLUTE 禁忌被全部过滤）时：

- **不返回空结果**——放弃过滤，将原始候选集送进重排序
- 但在最终回答中通过 `ContraindicationDetectionService.buildSafetyNote()` 附加兜底安全提示：
  > 您查询的内容涉及特定药物和人群，可能存在用药安全风险。以上信息仅供参考，请务必在医生指导下用药。
- 同时记录本次"空过滤"事件到日志，用于后续规则优化

### 6.3 第三级：置信度门控 + 回答安全校验 + 免责声明

第三级在 LLM 生成前后执行，由 `SafetyGuardService` 统一实现。分为三个子环节：

**文件**：`src/main/java/com/student/service/rag/SafetyGuardService.java`

#### 6.3.1 置信度门控（LLM 生成前）

`assessConfidence(rerankedResults)` —— 基于检索结果的最高重排序分数判断是否调用 LLM：

| 分数区间 | 决策 | 行为 |
|---------|------|------|
| `maxScore < 0.35` | **BLOCK** | 不调用 LLM，返回预设响应："抱歉，当前检索到的医学资料与您问题的相关性较低，无法生成可靠的回答……" |
| `0.35 ≤ maxScore < 0.6` | **WARNING** | LLM 正常生成，但在后续 `sanitizeAnswer` 中追加免责声明 |
| `maxScore ≥ 0.6` | **PASS** | LLM 正常生成，高于 0.8 时不追加免责声明 |

#### 6.3.2 回答安全校验（LLM 生成后）

`sanitizeAnswer(answer, confidence)` —— 净化 LLM 输出：

1. **危险模式替换**：正则匹配 `blockedPatterns`（如"建议(服用|使用|口服|注射).*药物"、"推荐.*(剂量|用量|用法)"等），命中后替换为 `[请遵医嘱用药]`
2. **免责声明追加**：当 `confidence < disclaimerMaxConfidence (0.8)` 时，在回答末尾追加：
   > 免责声明：以上信息仅供参考，不能替代专业医疗建议。如有身体不适，请及时前往医疗机构就诊。

#### 6.3.3 三级阈值总览

| 阈值 | 值 | 位置 | 触发行为 |
|------|-----|------|---------|
| `minThreshold` | 0.35 | `ConfidenceConfig` | 硬阻断，不调用 LLM |
| `warningThreshold` | 0.6 | `ConfidenceConfig` | 软警告，LLM 生成后追加免责声明 |
| `disclaimerMaxConfidence` | 0.8 | `AnswerSafetyConfig` | 免责声明添加上限，高于此值不追加 |

### 6.4 三级漏斗协同

三个级别在 RAG 管线中的位置和协同关系：

```
文档入库              检索阶段              LLM阶段              输出阶段
──────────────────────────────────────────────────────────────────────

[第一级]              [第二级]              [第三级]
来源可信度分级  ───→  药物-人群冲突检测  ───→  置信度门控      ───→  返回响应
(预处理时标注)        (质量过滤时执行)       (LLM生成前+后)

AuthorityLevel       Contraindication      SafetyGuardService
• 8级证据金字塔       • 禁忌过滤(4级降权)    • assessConfidence()
• 0.1 ~ 1.0 分数     • 矛盾检测(分级裁决)    • sanitizeAnswer()
• 写入chunk元数据     • 空候选集兜底          • 免责声明追加
```

**漏斗效应**：
- 第一级：所有入库文档全覆盖，为每个 chunk 赋予权威分数（宽度：100% 文档）
- 第二级：仅对检索召回的候选集进行冲突检测（宽度：top-K 检索结果）
- 第三级：仅对 LLM 的最终输出进行质量把控（宽度：单次回答）

每一级都在更窄的范围内进行更精细的检查，三层叠加形成纵深防御。

**协同规则**：
- 冲突时权威性高的来源在多因子重排序中自动覆盖权威性低的（第一级 → 第二级）
- 矛盾检测不再阻断管线，采用权威分级裁决：权威差距 ≥ 0.15 时以高权威方为准（RESOLVED），差距 < 0.15 时交 LLM 综合判断（UNRESOLVED），均在回答末尾附加相应安全提示（第二级 → 第三级）
- 全部被过滤时放弃过滤但强化免责声明（第二级 → 第三级）
- 置信度低的回答既附加免责声明又替换危险模式（第三级内部协同）

### 7.2 SafetyEvaluator（安全质量评估器）

**文件**：`src/main/java/com/student/service/evaluation/SafetyEvaluator.java`（接口）
`src/main/java/com/student/service/evaluation/impl/SafetyEvaluatorImpl.java`（实现）

核心评估指标：

| 指标 | 计算方法 | 含义 |
|------|---------|------|
| `emergencyDetectionAccuracy` | correctEmergency / expectedEmergency | 紧急检测准确率（应阻断中被正确阻断的比例） |
| `emergencyDetectionPrecision` | correctEmergency / actualEmergency | 紧急检测精确率（实际阻断中正确的比例） |
| `emergencyDetectionRecall` | 同 Accuracy | 召回率（二分类场景下等同准确率） |
| `safetyBlockRate` | (actualEmergency + actualConfidence) / n | 安全兜底总触发率 |
| `falseBlockRate` | falseBlocks / n | 误阻断率（不应阻断但被阻断的查询比例） |
| `confidenceGateEffectiveness` | correctConfidence / expectedConfidence | 置信度门控有效率 |

**输入数据来源**：`eval_query_result` 表中的 `emergencyTriggered`、`confidenceBlocked` 字段，与数据集标注的 `shouldTriggerEmergency`、`shouldTriggerConfidenceBlock` 字段对比计算。

## 十、急症关键词库设计

### 10.1 关键词组织原则

- **CRITICAL**：直接威胁生命，必须立即 120 / 急诊。匹配到这些词 → 100% 阻断 RAG。
- **HIGH**：可能迅速恶化，建议尽快就医。匹配到这些词 → 阻断 RAG，返回就医建议。
- **MEDIUM**：需要引起注意，但可等待常规就诊。匹配到这些词 → 阻断 RAG，返回就医建议。

### 10.2 关键词示例（完整列表约 60 个，按三类分）

**CRITICAL（20 个）**：

## 十一、阈值推荐与面试追问应对

| 阈值 | 值 | 作用 | 依据 |
|------|-----|------|---------|
| `min-threshold` | 0.35 | 硬阻断线，低于此值不调用 LLM | Cross-encoder 分数 < 0.3 通常为"不相关"，取 0.35 作为保守边界 |
| `warning-threshold` | 0.60 | 软提示线，添加免责声明 | Cross-encoder 分数 > 0.6 通常为"可靠相关" |
| `disclaimer-max-confidence` | 0.80 | 置信度 > 0.8 时不显示免责声明 | 高分回答已有充分证据，可减少对用户的干扰 |

**可配置化**：所有阈值在 `application.yml` 中可调，通过配置中心可动态下发。

**面试追问应对**：

- *问：0.35 和 0.6 是根据什么定的？有没有数据支撑？*
  答：初始阈值基于 cross-encoder reranker 的典型分数分布。Cross-encoder 的输出是 query-document 对的语义相似度，经验分布为：< 0.2 完全不相关，0.2-0.4 弱相关，0.4-0.6 部分相关，> 0.6 可靠相关。医疗场景取保守值。上线后我们会在生产环境收集分数分布数据，通过 ROC 曲线分析找到最优 cutoff。这也是为什么阈值设计为可配置的。

- *问：如果误判了（比如用户问"什么是胸痛"不是真的胸痛），会怎么样？*
  答：这种误判是已知的局限。当前方案采用了关键词精确匹配而非语义理解，所以"什么是胸痛"不会命中（因为触发词是"胸痛剧烈"而不是"胸痛"）。关键词的措辞特意加了程度限定词（剧烈、严重、持续等），大幅降低误判率。未来可引入 NER + 意图分类来进一步区分"询问症状"和"表达症状"。

- *问：有没有考虑过用分类模型代替关键词匹配？*
  答：考虑过。分类模型（例如 BERT-based 紧急分类器）准确率更高，但有三个问题：(1) 增加推理延迟和成本；(2) 需要标注数据训练；(3) 模型可能在某些边缘 case 上产生置信度错误的预测。关键词匹配虽然简单，但在医疗急症场景下，**宁可误判不可漏判**，关键词匹配的假阴性率更低。当前方案是"关键词+规则"作为第一道防线，未来可以叠加分类模型作为第二道防线。

## 十四、系统提示词与 LLM 集成

### 14.1 系统提示词中的安全兜底

**文件**：`src/main/resources/prompts/system.md`

在 LLM 系统提示词中定义了**安全兜底机制**章节，约束 LLM 行为：

- **安全第一原则**：当检索结果不足以安全回答时，必须触发安全兜底
- **安全兜底响应模板**：定义了标准化的安全响应格式
- **禁止行为**：不得在证据不足时给出确定性医疗建议

### 14.2 用户查询模板

**文件**：`src/main/resources/prompts/user-template.md`

用户查询模板中明确要求：*"安全第一：如果检索结果不足以安全回答，必须触发安全兜底"*

### 14.3 提示词与代码兜底的关系

提示词层面的安全约束是**软约束**（依赖 LLM 遵循指令），代码层面的安全兜底是**硬约束**（规则引擎强制执行）。两者互补：
- 代码兜底保证关键安全规则不会被 LLM 绕过
- 提示词兜底覆盖代码规则无法穷举的边缘场景（如 LLM 主动判断检索质量不足）

## 十五、HIS 采集与 SNOMED CT 降级

### 15.1 HIS 采集中的安全状态

**文件**：`src/main/java/com/student/service/his/AnalysisInput.java`

在 HIS 问卷分析模块中，`AnalysisInput` 包含 `SafetyStatusBlock`：

```java
public static class SafetyStatusBlock {
    private boolean hasEmergencyFlag;        // 是否检测到紧急标识
    private List<String> triggeredKeywords;  // 触发的关键词列表
    private boolean wasInterrupted;          // 采集是否被安全阻断中断
}
```

这使得 HIS 问卷采集流程也能受益于安全兜底机制——当用户填写的症状触发急症关键词时，采集流程被中断并返回就医建议。

### 15.2 SNOMED CT 本地降级映射

**文件**：`src/main/java/com/student/service/snomed/config/SnomedFallbackMapper.java`

当 Snowstorm 术语服务器不可用时，系统使用本地内存映射表进行术语标准化。该降级映射包含四类映射：

| 映射类型 | 规模 | 示例 |
|---------|------|------|
| 口语化表达 → SNOMED | ~35条 | "脑袋疼" → 22253000 (头痛) |
| 医学术语 → SNOMED | ~17条 | "糖尿病" → 44054006 |
| 症状关键词 → SNOMED | ~17条 | "疼" → 21522001 (疼痛) |
| 疾病关键词 → SNOMED | ~9条 | "肿瘤" → 108369006 |

口语化表达映射与急症关键词库形成互补——急症关键词用于**阻断**高危查询，SNOMED 降级映射用于**增强**正常查询的语义理解准确度。

## 十六、集成步骤

实际集成已按以下顺序完成：

1. **创建配置类**：`SafetyConfig.java`（绑定 `imkqas.rag.safety` 前缀，含三个内部配置类）
2. **创建值对象**：`SafetyDecision.java`、`ConfidenceDecision.java`
3. **创建核心服务**：`SafetyGuardService.java`（三层安全防护 + 统计计数器）
4. **配置 YAML**：在 `application.yml` 中追加 `imkqas.rag.safety` 完整配置段（急症关键词三级库 + 置信度阈值 + 回答安全规则）
5. **集成 QaServiceImpl**：在 `answer()` 和 `answerWithSources()` 两个方法的四个位置插入安全兜底调用（急症预检 → 置信度门控 → 答案净化 → 禁忌检测兜底）
6. **添加管线追踪**：在 `PipelineTraceContext` 中记录安全兜底三个步骤的耗时和中间状态
7. **创建评估数据集表**：执行 `V4__Evaluation_tables.sql` 迁移，创建 6 张评估相关表
8. **实现评估器**：`SafetyEvaluatorImpl`（安全质量评估）、`OnlineMetricsCollectorImpl`（在线指标采集）
9. **配置系统提示词**：在 `prompts/system.md` 和 `prompts/user-template.md` 中添加安全兜底约束
10. **前端适配**：在 `QaView.vue` 中添加安全提示条、安全警报卡片和管线步骤可视化
11. **HIS 模块集成**：在 `AnalysisInput` 中添加 `SafetyStatusBlock`
12. **测试覆盖**：创建 `SafetyFallbackTest.java`（7个测试用例）、`test_scenarios.json`（4个安全场景）
