# 意图路由设计方案

## Context

为后续对接 HIS 做准备，预留 FHIR R4 标准接口。同时实现 AI 填表助手和意图路由：用户输入先经路由判断，知识查询走 RAG 路径，数据采集走问卷路径，混合型走 RAG + 建议填表。采用"接口与实现分离"策略，通过 `imkqas.his.enabled` 开关控制数据源切换。

## 核心架构设计

### 意图路由（IntentRouter）

```
用户输入 → IntentRouter.classify(input)
  ├── KNOWLEDGE_QUERY → RAG 路径（现有 QaService，安全约束）
  ├── DATA_COLLECTION → 问卷路径（InterviewEngine）
  └── MIXED → RAG 回答 + 建议填表（LLM 生成回答 + 尾部附加问卷推荐）
```

路由判断策略（多层过滤架构）：
1. **Caffeine 本地缓存**（5min TTL，10,000 条上限）— 最快命中
2. **关键词规则** — 医疗问答关键词 → KNOWLEDGE；自评/症状描述 → DATA_COLLECTION
3. **正则匹配** — 关键词未命中时补充边界 case
4. **Redis 分布式缓存**（2h TTL）— 跨实例共享
5. **LLM 分类**（2s 超时 + 断路器保护）— 复杂场景语义理解
6. **兜底** — KNOWLEDGE_QUERY（保证可用性）

断路器机制：
- LLM 断路器：连续失败 5 次 → 熔断 30s → 半开试探
- Redis 断路器：第 1 次超时即熔断 30s → 半开试探（保守策略，保护下游）
- Redis 写入异步化，失败不影响主链路

### 状态机（ConversationStateManager）

```
CHAT ──(AI建议+用户确认)──→ QUESTIONNAIRE
QUESTIONNAIRE ──(完成/中断)──→ CHAT
QUESTIONNAIRE ──(超时30min)──→ CHAT（自动恢复）
```

- 状态存储在 Redis（TTL 30分钟），支持分布式
- 中断恢复：用户返回时检查是否有未完成的问卷会话
- 每个会话绑定 conversationId，与现有对话系统无缝衔接

### AI 填表助手原则

- **按需触发**：只在意图路由判断为 DATA_COLLECTION 或 MIXED 时触发
- **用户主导**：AI 建议问卷 → 展示问卷信息 → 用户确认后才进入问答流程
- **不主动打断**：知识查询类不推送问卷

### 双模采集架构

填表引擎支持两种采集模式，自动降级：

1. **LLM 驱动模式**（CollectionSubAgent）：自然语言对话采集，LLM 理解用户表述 → 语义映射到问卷选项 → 追问模式处理歧义
2. **纯表单模式**（Manual Form）：传统点击选项，逐题或批量提交
3. **自动降级**：LLM 连续失败 → 断路器触发 → 全量降级为纯表单模式；追问超限 → 单题降级为手动输入编号

### 三阶段确定性管线（TransformationPipeline）

```
阶段1: 完整性校验 → 必答题检查、答案合法性验证
阶段2: 规则计算 → 评分累加、风险等级判定、组合逻辑触发
阶段3: FHIR组装 → 生成 QuestionnaireResponse + DiagnosticReport + RiskAssessment
```

## 覆盖的 FHIR 资源（7 种）

| 资源 | 路径 | 建表 | 说明 |
|------|------|------|------|
| Patient | `/api/his/fhir/Patient` | fhir_patient_cache | 患者人口学信息 |
| Observation | `/api/his/fhir/Observation` | fhir_observation_cache | 生命体征、检验检查 |
| Condition | `/api/his/fhir/Condition` | fhir_condition_cache | 诊断/病情 |
| QuestionnaireResponse | `/api/his/fhir/QuestionnaireResponse` | fhir_questionnaire_response_cache | 问卷填写结果 |
| Bundle | `/api/his/fhir/Bundle` | 不建表（传输容器） | 统一写入入口，transaction/batch |
| DiagnosticReport | 通过 InterviewController 内部使用 | fhir_diagnostic_report_cache | AI 分析报告 |
| RiskAssessment | 通过 InterviewController 内部使用 | fhir_risk_assessment_cache | AI 风险评估 |

## 核心流程

### 意图路由分流

```
用户: "糖尿病患者应该怎么饮食？"
  → IntentRouter.classify() → KNOWLEDGE_QUERY
  → 走现有 RAG 路径（12 步管线），返回知识回答

用户: "最近一周情绪很低落，睡不好"
  → IntentRouter.classify() → DATA_COLLECTION
  → InterviewEngine.suggestQuestionnaire() → 匹配到 PHQ-9
  → 返回: "您描述的情况可能适合PHQ-9抑郁筛查量表，是否需要填写？（共9题，约3分钟）"

用户确认 "好的"
  → ConversationStateManager.transition(CHAT → QUESTIONNAIRE)
  → InterviewEngine.startInterview("PHQ-9", userId, conversationId)
  → 返回第1题...（纯表单模式 或 LLM 驱动模式）

用户: "糖尿病有什么症状？我最近总是口渴"
  → IntentRouter.classify() → MIXED
  → RAG 回答糖尿病症状知识
  → 尾部附加: "您提到口渴的症状，是否需要填写糖尿病风险自评表？"
```

### 意图路由多层过滤流程

```
用户输入
  → [0] Caffeine 本地缓存命中? → 返回缓存结果
  → [1] 关键词匹配
     - DATA_COLLECTION关键词 + 问卷匹配 → DATA_COLLECTION
     - KNOWLEDGE关键词 + 无DATA关键词 + 无问卷匹配 → KNOWLEDGE_QUERY
  → [2] 正则匹配（关键词未命中时补充）
  → [3] Redis 分布式缓存（断路器保护）
  → [4] LLM 分类（2s超时 + 断路器，连续5次失败熔断30s）
  → [5] 兜底 → KNOWLEDGE_QUERY
```

### 双模采集流程

```
LLM驱动模式:
  用户自然语言输入
    → CollectionSubAgent 语义理解
    → 匹配到具体选项（含置信度）
    → 置信度高 → 记录答案 → 下一题
    → 置信度低 → CLARIFY追问（最多5次）
    → 追问超限 → 降级为规则解析器 → 再超限 → 纯表单模式

纯表单模式:
  前端展示题目 + 选项
    → 用户点击选项 → answerQuestion()
    → 或一次性填写所有剩余题目 → submitBatch()
```

### 状态机转换（含生命周期）

```
CHAT
  │  AI建议问卷 + 用户确认
  ▼
QUESTIONNAIRE (ACTIVE → QUESTIONING)
  │  每次回答 → ANSWER_RECEIVED
  │  需要追问 → CLARIFYING
  │  全部答完 → COMPLETED → generateResponse() → CHAT
  │  用户取消 → cancel() → ABANDONED → CHAT
  │  用户暂停 → pause() → PAUSED → 定时清理(5min) → EXPIRED
  │  超时30min → 自动恢复 → EXPIRED → CHAT
  ▼
CHAT
```

## 设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 路由分类 | 多层过滤：Caffeine → 关键词 → 正则 → Redis → LLM(2s超时+断路器) → 兜底 | 逐层降级，保证高可用；LLM 准确率高，关键词/正则保证可用性 |
| LLM 断路器 | 连续失败5次熔断30s | 防止 LLM 不可用时持续超时堆积 |
| Redis 断路器 | 第1次超时即熔断30s | 保守策略，快速失败保护下游 |
| 状态存储 | Redis（TTL 30min）+ MySQL 冷存储 + 本地 Map 兜底 | 分布式支持，自动过期，多层降级 |
| 意图路由位置 | QaServiceImpl 入口处 | 与现有 RAG 流程无缝衔接，单点控制 |
| 填表触发 | 用户确认后才进入 | 用户主导，不主动打断知识问答 |
| 混合型处理 | RAG 回答 + 尾部附加建议 | 不影响知识问答体验 |
| 采集模式 | LLM 驱动 + 纯表单双模，自动降级 | LLM 体验好但不可靠，纯表单作最终兜底 |
| 分析报告 | 三阶段管线 + LLM 生成结构化报告 | 规则计算保证确定性，LLM 提供共情和建议 |
| FHIR 资源 | 扩展至 7 种（含 DiagnosticReport, RiskAssessment） | 支持完整的数据采集→分析→评估闭环 |
