# 置信度权重测试执行手册

> **适用场景**：文档总量 < 5000，无真实搜索日志，使用 LLM 双流水线生成测试集 + 标注相关性。
> **评估指标**：MRR@All（主）+ Recall@3（辅）
> **策略**：5 组预设权重直接对比，不进行贝叶斯调参。

---

## 第一部分：测试数据集构建（LLM 双流水线）

### 1.1 准备工作

1. 从知识库导出所有文档的 `标题 + 摘要（或正文前200字）`，生成一个 JSON 数组文件 `docs.json`。
2. 确认生成 Query 的 LLM 与标注相关性的 LLM **不是同一个会话**（或使用不同模型），避免偏见。

### 1.2 流水线一：生成 Query

将以下 Prompt 复制到 LLM 对话中，并附带 `docs.json` 的内容：

```
你是一位医疗搜索质量测试专家。你需要为以下文档生成用户搜索 Query，用于评估搜索引擎的排序质量。

## 输入
我会给你一个 JSON 数组，每个元素包含：
- id: 文档唯一标识
- title: 文档标题
- summary: 文档摘要（正文前200字）

## 任务
为每篇文档生成 3 种类型的 Query：

| 类型 | 名称 | 说明 | 示例 |
|------|------|------|------|
| A | 直接命中 | 搜索文档核心名词，用户知道要找什么 | "小儿肺炎的症状有哪些" |
| B | 行为意图 | 问"怎么做/如何解决/怎么判断"，用户有实际问题要解决 | "孩子发烧38度怎么办" |
| C | 长尾边界 | 弱相关或边缘场景，测试系统抗噪能力 | "换季时宝宝皮肤干燥起皮怎么护理"（文档讲湿疹） |

## 输出格式
返回一个 JSON 数组，每个元素格式如下：
```json
{
  "doc_id": "文档id",
  "queries": [
    {"type": "A", "text": "直接命中型Query"},
    {"type": "B", "text": "行为意图型Query"},
    {"type": "C", "text": "长尾边界型Query"}
  ]
}
```

## 硬性约束
1. 每个 Query 长度 3~15 字（中文），口语化风格。
2. 禁止使用"本文""这篇文章""根据文档""该文献"等词。
3. Query 必须是真实用户可能在搜索框输入的内容，不是学术论文标题。
4. 类型 C 的 Query 与文档主题必须有至少一个交叉词，但不能直接匹配标题核心词。
5. 禁止生成重复或高度相似的 Query。
6. 类型 B 的 Query 必须包含行为动词（怎么做、如何、怎么办、怎么判断等）。
```

**输出文件**：将结果保存为 `queries.json`，格式为扁平化的 `(query, doc_id, type)` 列表。

### 1.3 流水线二：标注相关性

**重要**：使用与 1.2 不同的 LLM 或开启全新会话，避免上下文污染。

将以下 Prompt 复制到新会话中，附带 `queries.json` 和 `docs.json`：

```
你是一位严格的医学信息检索裁判。你需要对每个(查询, 文档)对进行相关性打分。

## 评分标准

| 分数 | 含义 | 判定规则 |
|------|------|----------|
| 2 | 直接完整回答 | 文档内容能**直接、完整**地回答Query提出的问题。必须包含核心答案句。 |
| 1 | 提及主题但未给答案 | 文档涉及Query的主题领域，但**没有给出具体答案**，或只提供了背景/定义。 |
| 0 | 答非所问 | 文档内容与Query无关，或相关度极低。 |

## 严格判定规则（必须遵守）

1. **意图匹配优先**：若Query问"怎么做/步骤/如何处理"，而文档只讲"定义/分类/原理"，直接判为 1 分，不得给 2 分。
2. **核心答案句检测**：给 2 分前，你必须在文档中找到至少一句"核心答案句"——这句子能直接回答Query的问题。找不到则不給 2 分。
3. **否定信规则**：如果文撒只提到Query中的关键词，但没有展开讲该关键词与Query意图的关系，最多给 1 分。
4. **同义词判例**：Query和文档使用不同但等价的医学术语（如"发热"vs"发烧"）不影响评分。

## 输入
- queries.json: 包含 (query_id, query_text, doc_id) 的数组
- docs.json: 包含文档 (id, title, summary) 的数组

## 输出格式
返回一个 JSON 数组：
```json
[
  {"query_id": "q001", "query_text": "...", "doc_id": "d001", "score": 2},
  {"query_id": "q001", "query_text": "...", "doc_id": "d002", "score": 0}
]
```
仅输出 id 和 score，不需要解释理由。

## 质量要求
- 给 2 分前，在心中默念一遍文档的核心答案句，确认其确实回答了Query。
- 你是一位**严格批判的裁判**，倾向于给低分而非高分。只有确凿无疑时才给 2 分。
- 标签分布大致应为 2:1:0 ≈ 3:4:3。如果你的 2 分占比超过 35%，说明你的标准太松，请重新审视。
```

### 1.4 标注后质检

完成标注后，统计标签分布：

```
2分占比 = count(score=2) / total
1分占比 = count(score=1) / total
0分占比 = count(score=0) / total
```

**健康标准**：2:1:0 ≈ 3:4:3（即 2 分约 30%，1 分约 40%，0 分约 30%）。

| 异常情况 | 处理方式 |
|----------|----------|
| 2 分 > 50% | 标注过松，重新执行 1.3，在 Prompt 中追加"上次 2 分占比过高，本次请更加严格，必须包含核心答案句才给 2 分" |
| 0 分 > 50% | Query 与文档匹配度过低，检查 1.2 生成的类型 C Query 是否过于偏离 |
| 1 分 > 60% | 标注过于保守，重新执行 1.3，追加"如果文档确实完整回答了Query，请大胆给 2 分" |

## 第二部分：评估指标定义

### 2.1 MRR@All（Mean Reciprocal Rank @ All）

**公式**：

```
MRR@All = (1 / |Q|) × Σ_{q∈Q} (1 / rank_q)
```

其中：
- `Q` = 所有测试 Query 集合
- `rank_q` = 对于 Query q，**第一个 Label=2（直接完整回答）的文档**在排序结果中的位置（从 1 开始）
- 若排序结果中**没有任何** Label=2 的文档，`1 / rank_q = 0`

**物理含义**：正确答案出现在排序结果多靠前的位置。MRR=1.0 表示每个 Query 的正确答案都在第 1 位；MRR=0.5 表示正确答案平均在第 2 位。

**计算示例**：

| Query | 排序结果（文档ID→Label） | 第一个Label=2的位置 | 1/rank |
|-------|-------------------------|--------------------|--------|
| q1 | d3(1)→d1(2)→d2(0) | 2 | 0.5 |
| q2 | d5(2)→d2(1)→d7(0) | 1 | 1.0 |
| q3 | d1(1)→d4(0)→d8(1) | 无 | 0.0 |

MRR@All = (0.5 + 1.0 + 0.0) / 3 = 0.5

### 2.2 Recall@3（Recall at Top 3）

**公式**：

```
Recall@3 = (1 / |Q|) × Σ_{q∈Q} I(前3条结果中至少包含1个Label=2的文档)
```

其中 `I(条件)` 为指示函数，条件成立为 1，否则为 0。

**物理含义**：用户只看前 3 条结果时，有多大比例能找到正确答案。Recall@3=0.9 表示 90% 的 Query 在前 3 条就能找到答案。

**计算示例**：

| Query | 前3条结果 | 含Label=2? |
|-------|----------|-----------|
| q1 | d3(1), d1(2), d2(0) | 是 |
| q2 | d5(2), d2(1), d7(0) | 是 |
| q3 | d1(1), d4(0), d8(1) | 否 |

Recall@3 = 2/3 ≈ 0.667

### 2.3 底线标准

| 指标 | 底线值 | 说明 |
|------|--------|------|
| MRR@All | > 0.75 | 低于此值说明排序质量不足 |
| Recall@3 | ≥ 0.85 | 低于此值说明召回环节有问题 |

**若任一指标不达标**：暂不继续权重对比，先排查：
1. 语义检索（embedding 模型）的召回质量
2. 关键词检索的覆盖率
3. 文档分块策略是否合理

## 第三部分：5 组待测权重

### 3.1 权重配置表

| 编号 | 名称 | authority | timeliness | semantic | intent | hierarchy | 测试目的 |
|------|------|-----------|------------|-----------|--------|-----------|----------|
| A | 语义主导 | 0.15 | 0.10 | 0.40 | 0.20 | 0.15 | 验证高语义占比是否在小样本下导致过拟合虚高 |
| B | 结构主导 | 0.15 | 0.10 | 0.25 | 0.15 | 0.35 | 验证小样本场景下标题/层级匹配是否为最稳健信号 |
| C | 意图优先 | 0.20 | 0.10 | 0.25 | 0.30 | 0.15 | 验证意图识别对医学查询消歧的必要性和贡献 |
| D | 权威+时效 | 0.30 | 0.25 | 0.20 | 0.15 | 0.10 | 验证来源可信度和内容时效性在医学场景的权重 |
| E | 当前配置（基线） | 0.20 | 0.15 | 0.40 | 0.15 | 0.10 | 对照组，当前生产环境实际使用的权重 |

> **注意**：E 组为当前 `application.yml` 中 `imkqas.rag.multi-factor-rerank.weights` 的实际值，与代码 `RagConfig.MultiFactorRerankConfig.FactorWeights` 默认值一致。

### 3.2 修改权重的方法

在 `application.yml` 中修改配置后重启服务：

```yaml
imkqas:
  rag:
    multi-factor-rerank:
      weights:
        authority: [待填值]
        timeliness: [待填值]
        semantic: [待填值]
        intent: [待填值]
        hierarchy: [待填值]
```

或者通过调用 `/api/rag/retrieval-test/factor-breakdown` 获取逐文档的原始因子得分后，在 Python 脚本中离线应用不同权重计算最终得分（无需反复重启服务）。

## 第四部分：测试执行流程（3 轮定稿）

### 前置条件

- [ ] `docs.json` 已准备完毕（所有文档的标题+摘要）
- [ ] `queries.json` 已由流水线一生成（约 documents × 3 条 Query）
- [ ] `labels.json` 已由流水线二标注完毕（每个 (Query, Doc) 对的 0/1/2 标签）
- [ ] 标签分布已通过质检（2:1:0 ≈ 3:4:3）
- [ ] IMKQAS 服务已启动，`/api/rag/retrieval-test/factor-breakdown` 端点可访问

### 第 1 轮：粗筛（淘汰 2 组）

**目标**：快速排除表现最差的 2 组权重。

**操作步骤**：

1. 对每个测试 Query，调用 `/api/rag/retrieval-test/factor-breakdown` 获取每个文档的原始五因子得分（authority, timeliness, semantic, intent, hierarchy）。

2. 分别用 A/B/C/D/E 五组权重计算最终得分：
   ```
   finalScore = wAuthority × authority + wTimeliness × timeliness + wSemantic × semantic + wIntent × intent + wHierarchy × hierarchy
   ```

3. 按 finalScore 降序排列，得到每组权重下的文档排序。

4. 对照 `labels.json`，计算每组权重的 MRR@All 和 Recall@3。

5. 按 MRR@All 降序排列，得到排名。

**决策规则**：
- 淘汰 MRR 最低的 2 组。
- 若第 3 名和第 4 名 MRR 差距 < 0.03，则都保留进入第 2 轮（即保留 4 组）。
- 若某组 Recall@3 < 0.85，即使 MRR 高也要标记为"召回不稳定"，优先考虑淘汰。

**产出**：第 1 轮测试报告，含 5 组的 MRR@All、Recall@3、排名，以及晋级/淘汰结论。

### 第 2 轮：消融测试

**目标**：量化 semantic 和 hierarchy 两个维度的真实贡献，判断是否有冗余维度。

**操作步骤**：

1. 对第 1 轮晋级的 3 组权重，分别创建消融变体：

   **消融 A（砍 semantic）**：
   - 将 semantic 强制置 0
   - 其他 4 个维度**按原比例等比例放大**补足至 1.0
   - 例如原权重 (0.15, 0.10, 0.40, 0.20, 0.15)，semantic 去零后剩余和为 0.60，则各维度 × (1/0.60)

   **消融 B（砍 hierarchy）**：
   - 将 hierarchy 强制置 0
   - 其他 4 个维度等比例放大补足至 1.0

2. 用消融后的权重重新计算 MRR@All。

3. 计算 MRR 跌幅：
   ```
   跌幅 = (原MRR - 消融后MRR) / 原MRR × 100%
   ```

**决策规则**：

| 跌幅 | 结论 | 行动 |
|------|------|------|
| < 3% | 该维度几乎无用 | 可从最终配置中移除，权重补给其他维度 |
| 3%~10% | 该维度有弱贡献 | 保留但可适当降低权重 |
| > 10% | 该维度为关键因子 | 必须保留且保持当前权重 |

**产出**：消融测试报告，含每个晋级组的 MRR 跌幅对比和维度重要性结论。

### 第 3 轮：人工盲测

**目标**：通过人工判断确认最终获胜权重，避免纯指标优化的过拟合。

**操作步骤**：

1. 从测试集随机抽取 **20 个 Query**（确保包含类型 A/B/C 各约 1/3）。

2. 对每个 Query，用晋级的 3 组权重分别排序，取 Top 5 文档，打印成**盲测卡**：
   ```
   ┌─────────────────────────────────────────────┐
   │ Query #7: 小儿发热惊厥怎么处理               │
   │                                             │
   │ 方案 X:  1. 热性惊厥诊疗指南                 │
   │          2. 小儿发热的护理要点                │
   │          3. 儿童布洛芬使用说明                │
   │          4. 惊厥的鉴别诊断流程                │
   │          5. 发热的病理生理机制                │
   │                                             │
   │ 方案 Y:  1. 热性惊厥诊疗指南                 │
   │          2. 惊厥的鉴别诊断流程                │
   │          3. 小儿发热的护理要点                │
   │          4. 儿童布洛芬使用说明                │
   │          5. 儿科急症处理原则                  │
   │                                             │
   │ 方案 Z:  1. 小儿发热的护理要点                │
   │          2. 热性惊厥诊疗指南                 │
   │          3. 发热的病理生理机制                │
   │          4. 儿童布洛芬使用说明                │
   │          5. 惊厥的鉴别诊断流程                │
   └─────────────────────────────────────────────┘
   ```
   - 方案 X/Y/Z 的对应关系对评审者**隐藏**。
   - 每组盲测卡的 X/Y/Z 随机排列，避免位置偏见。

3. 邀请 **3 位业务同事**独立投票（每人20票），选出每个 Query 下"最好的排序结果"。

4. 揭盲后统计每组权重的总得票数。

**决策规则**：
- 票数最高者为最终定稿权重。
- 若最高票与次高票差距 ≤ 2 票，需组织一轮讨论后重新投票。
- 若第 1 轮 MRR 最高的组与盲测得票最高的组不一致，以盲测结果为准。

**产出**：盲测投票记录和最终定稿结论。

## 第五部分：最终决策逻辑

### 5.1 获胜组 → 调整建议

| 获胜组 | 调整策略 |
|--------|----------|
| **A 组胜出**（语义主导） | 维持当前语义权重 0.40，或小幅降至 0.35。说明语义信号在小样本下已有足够区分度。 |
| **B 组胜出**（结构主导） | 将 semantic 降至 0.25，hierarchy 升至 0.30~0.35。小样本下标题/层级匹配是最稳健的信号。 |
| **C 组胜出**（意图优先） | 将 intent 提升至 0.30，semantic 降至 0.25。说明意图消歧对医学查询排序贡献显著。 |
| **D 组胜出**（权威+时效） | 将 authority 升至 0.30，timeliness 升至 0.25，semantic 压低至 0.20。说明来源可信度比语义相似度更重要。 |
| **E 组胜出**（当前基线） | 保持当前配置不变。说明现有权重已经过充分调优，无需调整。 |

### 5.2 维度冗余处理

如果消融测试（第 2 轮）显示某维度可砍（MRR 跌幅 < 3%）：

**优先把省出的权重补给 hierarchy**，原因：
- 小样本场景下，文档的标题/层级结构是最可靠、最不易过拟合的信号。
- semantic 在小样本下容易产生虚假的高相似度，hierarchy 反而更稳健。

**分配示例**：

```
消融结论：砍掉 timeliness（跌幅 1.2%，可忽略）
原权重：  authority=0.20, timeliness=0.15, semantic=0.40, intent=0.15, hierarchy=0.10
调整后： authority=0.20, timeliness=0,    semantic=0.40, intent=0.15, hierarchy=0.25
                                                                    ↑ 0.10 + 0.15（省出）= 0.25
```

### 5.3 最终配置落地

1. 将最终定稿的权重值写入 `application.yml`：
   ```yaml
   imkqas:
     rag:
       multi-factor-rerank:
         weights:
           authority: [最终值]
           timeliness: [最终值]
           semantic: [最终值]
           intent: [最终值]
           hierarchy: [最终值]
   ```

2. 重启服务后，运行一轮 `hallucination_test.py`（`scripts/hallucination/`）确认权重变更未引入回归。

3. 将测试全过程的中间文件（`queries.json`, `labels.json`, 各轮结果）归档到 `scripts/confidence/confidence_tuning_results/`。
